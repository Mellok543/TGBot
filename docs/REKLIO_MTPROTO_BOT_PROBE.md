# Проверка удаления поста через MTProto от имени Reklio Bot

Цель: подтвердить, что наш **бот**, без отдельного пользовательского аккаунта, видит уже опубликованный пост по ID и отличает его от удалённого.

## Подготовка (один раз)

В GitHub → Settings → Environments → production → Environment secrets добавьте:
- `TELEGRAM_API_ID` — числовой `api_id` своего приложения на my.telegram.org
- `TELEGRAM_API_HASH` — `api_hash` этого приложения
- `BOT_TOKEN` — токен уже существующего Reklio Bot

Не добавляйте значения в исходный код, workflow YAML, issue, чат или логи. MTProto требует `api_id` и `api_hash` даже при авторизации токеном бота.

## Проверка

1. В тестовом канале, где Reklio Bot — администратор, создайте безобидное тестовое сообщение. Для начала лучше использовать **публичный** канал с `@username`.
2. Запомните ID сообщения: это число в ссылке на пост `https://t.me/channelname/123` (здесь ID — 123).
3. GitHub → Actions → **Reklio MTProto bot probe** → Run workflow. Укажите `channel=@channelname`, `message_id=123`.
4. В логах ожидается `PRESENT`.
5. Удалите этот тестовый пост вручную в Telegram. С теми же полями снова запустите workflow. Ожидается `MISSING`.

### Варианты результатов
- `PRESENT`: Telegram вернул сообщение по ID.
- `MISSING`: Telegram вернул `MessageEmpty`.
- `PEER_NOT_RESOLVED`: для приватного канала не удалось получить `access_hash` по одному числовому ID. Это **не** означает удаление сообщения.
- `TELEGRAM_ERROR`: ошибка авторизации, доступа или ограничения Telegram, а **не** доказательство удаления.
- `CONFIG_MISSING`: не заданы необходимые секреты.

Сначала проверьте метод на публичном тестовом канале. Для приватных каналов потребуется отдельная проверка механизма получения `InputChannel` и `access_hash`.

Это только диагностический тест: он ничего не публикует, не удаляет, не переводит заказы в спор и не управляет финансами. Не включайте автоматическую санкцию по одиночному `MISSING` без повторной проверки и проверки доступа к каналу.
