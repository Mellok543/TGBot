# Проверка рекламного маркетплейса перед запуском

Эта ветка содержит единый набор изменений рекламных заказов. Реальная оплата размещений в рублях через ЮKassa **не подключена**. Не используйте тестовую оплату как подтверждение поступления денег.

## Перед запуском
1. Дождитесь успешной GitHub Actions сборки PR #28.
2. Сделайте резервную копию MariaDB. Запускайте миграции из `Database.InitializeAsync` только на тестовой базе, затем на рабочей.
3. Установите `BOT_TOKEN`, `DATABASE_URL`, `ADMIN_TELEGRAM_ID` в окружении Pterodactyl. Не сохраняйте токены в Git.
4. Проверьте права бота на публикацию и удаление сообщений в тестовом канале.
5. Разрешите тестовый режим только выделенному тестовому аккаунту через админ-интерфейс.

## Сквозной сценарий
1. Зарегистрируйте рекламодателя и владельца канала; подключите тестовый канал, включите каталог и задайте цену.
2. Рекламодатель создаёт заказ, выбирает время публикации; владелец подтверждает. Статус должен стать `AwaitingPayment`, **не** `Paid`.
3. Тестовый рекламодатель нажимает «Тестовая оплата». Проверить `TestPaid`, `is_test_order=TRUE`, `payout_status=NotEligible`.
4. Проверить карточку, историю событий, уведомление владельцу, автоматическую публикацию и последующее удаление.
5. Проверить ошибку публикации при отсутствии прав бота; заказ не должен считаться опубликованным.
6. Открыть спор после публикации, дождаться истечения срока размещения: сообщение удаляется, но спор и блокировка выплаты сохраняются.
7. Администратор записывает решение по спору. Проверить уведомления участников; никаких реальных денежных операций быть не должно.
8. Проверить отклонение заявки владельцем и уведомление рекламодателю.
9. Заблокировать бота одним тестовым пользователем: уведомление должно перейти в `Failed` при постоянной ошибке Telegram; при временной ошибке — повторяться с задержкой.
10. Перезапустить бота при ожидающих уведомлениях; очередь должна продолжить обработку.

## Диагностика MariaDB
```sql
SELECT id,status,payment_status,payout_status,is_test_order FROM ad_requests ORDER BY id DESC LIMIT 20;
SELECT order_id,event_type,created_at FROM ad_order_events ORDER BY id DESC LIMIT 30;
SELECT id,order_id,recipient_id,state,attempts,last_error FROM notification_outbox ORDER BY id DESC LIMIT 30;
```

## Ограничения
- ЮKassa, реальные списания, возвраты и выплаты владельцам не активированы.
- Очередь уведомлений обеспечивает повторные попытки, но не строгую доставку ровно один раз: после сбоя возможны повторные сообщения.
- В текущей схеме события заказа и изменение статуса не всегда записываются в одной транзакции.
- Перед промышленным использованием требуется тестирование MariaDB, Telegram API, прав доступа и восстановления после сбоев.

## Мониторинг в боте
Откройте `/admin` → «🩺 Состояние заказов и очереди». Экран показывает количество ожидающих, отправляемых и недоставленных уведомлений, зависшие публикации и заказы с ошибками. Зависшие `Publishing` не переотправляйте автоматически: сначала проверьте, не был ли пост опубликован в Telegram до сбоя записи в БД.

## Проверка отказоустойчивости
Отключите доступ к Telegram только на тестовом окружении. Убедитесь, что ошибка одного заказа не блокирует обработку следующих и что отправка уведомлений продолжается после ошибок публикации. Повторный запуск планировщика не должен автоматически перепубликовывать заказы в `Publishing`.

## Работа с недоставленными уведомлениями
В /admin откройте «📨 Недоставленные уведомления». Список показывает ID уведомления, заказ, адресата, число попыток и последнюю ошибку. Кнопка «Повторить» сбрасывает счётчик только для записей в состоянии Failed. Убедитесь, что пользователь разблокировал бота и ошибка устранена: иначе уведомление снова завершится ошибкой. Не нажимайте повторно, если уведомление могло быть доставлено, но подтверждение в БД не записалось: Telegram не поддерживает idempotency key для SendMessage.

## Каталог, избранное и отзывы
1. Откройте «Покупка рекламы» → «Каталог», выберите категорию, сортировку и страницу. В карточке проверьте стоимость, форматы, опыт и отзывы.
2. Нажмите «❤️ В избранное», затем проверьте «Избранные каналы» в кабинете рекламодателя. Повторное нажатие должно удалить канал из избранного.
3. После **реального** оплаченного и опубликованного размещения откройте заказ рекламодателем: доступна оценка 1–5 звёзд и комментарий до 500 символов. Одна оценка на заказ, повторное нажатие меняет её.
4. У владельца, постороннего пользователя, тестового заказа и спорного заказа кнопки оценки быть не должно; прямой callback тоже должен отклоняться на уровне БД.
5. Проверьте среднюю оценку и список отзывов в карточке канала. Пока реальные платежи выключены, система намеренно не позволяет создавать «проверенные» отзывы на тестовых оплатах.

## Варианты длительности и цены
1. В настройках канала откройте «Сроки и цены рекламы» и добавьте `24 1600` и `48 3000`.
2. Повторное добавление `24 1800` должно обновить стоимость существующего 24-часового варианта, а не создать дубль.
3. Рекламодатель выбирает пакет (срок и цена), затем независимо от него дату и время публикации. В заказ должны записаться выбранная цена и срок удаления.
4. Проверьте удаление пакета и запрет редактирования чужого канала. При отсутствии пакетов действует старый выбор даты и общая цена.
5. Попробуйте забронировать через старую кнопку или устаревший callback: при активных пакетах обходить их нельзя.
